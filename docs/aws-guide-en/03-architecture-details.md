# Architecture details

> **Note (data-plane model transitioned)**
>
> The data plane in this chapter is described according to the **two-tier routing** model introduced by the 2026-07-08 de-hubbing redesign (platform backend WebSocket gateway → OpenResty edge → microVM gateway). It replaces the earlier model of a claw-hub WebSocket hub + claw-channel outbound dialing + three Amazon Cognito identities + an HMAC channel_secret; the old model's components have been removed from the deployment code and archived. For the full data-plane chain, timeouts, and scale baseline, see [Chapter 13 · Data-plane two-tier routing](13-data-plane-redesign.md). For the rationale, see `engineering/00-knowledge-base/decisions/DECISION-drop-oidc-cognito-use-openclaw-native-auth.md`.

This section describes the components and AWS services that make up this solution, along with details of how these components work together. The solution comprises three major components: a control plane (lifecycle management plane) responsible for registration, lifecycle, backup, and deregistration; a data plane (two-tier routing) that connects real-time chat directly to the gateway inside each tenant's microVM; and tenant microVMs (independent-kernel runtimes based on Firecracker) that run an OpenClaw AI agent with identity, skills, and guardrails for each tenant. The three responsibilities are orthogonal: the control plane performs lifecycle management only and injects no business data into a microVM after startup; the data plane performs per-tenant message routing only; and the tenant microVM is an isolated runtime that is a finished product at startup. The security model is layered on top of these three components as five layers of defense in depth, described in "Defense in depth: the five-layer security model" in this section.

## Control plane (lifecycle management plane)

This section describes the component composition and responsibility boundaries of the control plane. This component is built from AWS Lambda, Amazon DynamoDB, and Amazon API Gateway, is deployed through the AWS Cloud Development Kit (AWS CDK), and is responsible for tenant registration, start/stop, backup, migration, and deregistration. It does not participate in the real-time chat path.

The control plane exposes a set of REST APIs, all fronted by Amazon API Gateway and requiring `x-api-key`, backed by a single AWS Lambda function that serves endpoints for tenant registration, lifecycle operations, backup, host/skill/group management, and audit logging. Control plane state is persisted in Amazon DynamoDB, with three core state tables organized by responsibility as follows (plus an audit table and operational/federation helper tables such as batch-jobs and tenant-idp-map):

- **tenants table**: A schemaless table keyed on `id`, writing fields such as `owner_id`, `tenant_user_id`, `authorized_users`, and `litellm_vkey` on demand, carrying tenant metadata and authorization records; the KMS ciphertexts of the gateway token and the device private key are stored separately in the `openclaw-tenant-secrets` table. There is no complete table-level schema to reference.
- **hosts table**: Records host node status, specifications, and capacity counts (accounting for the overcommit ratio, available capacity = (total × ratio) − used).
- **groups table**: Records the skill set for each group, used to resolve a tenant's effective skills by group.

The control plane follows the "zero runtime operations" discipline: after a microVM starts, the control plane performs no behavioral or data injection into the running VM, and the host performs only lifecycle, resource, and network management. Modifying tenant identity, skills, or configuration requires rebuilding the image and performing a rolling rebuild, rather than calling a runtime API. Identity, skills, credentials, and configuration are cold-injected into the read-only golden image disk and data disk before the VM starts, and no bulk hot-injection channel from host to VM is opened after startup.

A control plane registration request defines the startup parameters for each VM: `tenant_id`, `vm_num`, along with `vcpu` (script default 2) and `mem_mb` (script default 4096).

> **Note**
>
> The `vcpu` default of 2 and `mem_mb` default of 4096 are startup-script defaults and differ from the steady-state capacity estimated at 2 GB/VM (the defaults are larger). The capacity descriptions in this guide consistently use the 2 GB/VM basis.

The control plane lifecycle operations have measured data with time anchors: the registration API returns in about 1.7s, creating→running availability is about 4.0s, hibernation (stop→stopped) about 6.0s, wakeup (start→running) about 3.7s, backup about 6.6s (artifact about 9.5MB), deregistration (DELETE→deleted) about 12.2s, and backup restore about 16s (9MB backup) — all lifecycle-measured.

Data protection for the control plane tables and protection for tenant business data are two independent mechanisms: the four `RETAIN` tables (tenants, hosts, groups, and audit) all have Point-in-Time Recovery (PITR) enabled (35 days of continuous backup by default, recoverable to any point within the recovery window), preventing control plane metadata from being unrecoverable after accidental deletion, modification, or corrupted writes; tenant business data, by contrast, is delivered by the backup Lambda to an Amazon S3 bucket with Object Lock (COMPLIANCE) enabled. PITR is config-gated (`dynamodb.point_in_time_recovery` defaults to true), on by default in code and inherited across rebuilds.

> **Note**
>
> Customer managed key (CMK) encryption for the Amazon DynamoDB audit table is currently planned (not implemented). The existing tables are `RETAIN`, and switching encryption online would force a replace and lose audit data, so it is planned only when a brand-new account is first deployed.

## Data plane (two-tier routing)

This section describes the connection model and identity planes of the data plane. The data plane connects real-time chat from browsers or front ends directly, by `tenant_id`, to the OpenClaw gateway inside the corresponding microVM; the microVM exposes the gateway port only on the host-internal TAP interface and opens no public inbound access. For the full chain, the timeout chain, and the 100k-scale baseline, see [Chapter 13 · Data-plane two-tier routing](13-data-plane-redesign.md); this section gives only an overview of the connection model and identity planes.

The data plane is an opt-in capability, controlled by `edge.enabled` and `redis.enabled` in `config.yml`, both off by default; once enabled, the chain is:

```
Browser ── wss /gw/ws ─▶ platform backend WebSocket gateway
  platform backend gateway ── ws ─▶ CloudFront ─▶ ALB ─▶ OpenResty edge ASG
    OpenResty edge ── ElastiCache Valkey/Redis route:{tenant_id} lookup ─▶ host iptables DNAT ─▶ microVM gateway:18789
```

Identity divides into two orthogonal planes, neither of which depends on Amazon Cognito any longer:

- **First hop (browser ↔ platform backend gateway)**: The browser connects to `/gw/ws` with a platform session token via `?token=`; the platform backend verifies it as a self-signed HS256 JWT (symmetric key, not Cognito RS256) and disconnects on failure (fail-closed). The front end touches no keys.
- **Second hop (platform backend gateway ↔ microVM gateway)**: The platform backend connects as a WebSocket client to the edge-exposed `/ws/{tenant_id}`, authenticating with OpenClaw's native Ed25519 device asymmetric handshake — on receiving `connect.challenge`, it signs with the device private key and replies with a `connect` frame, also carrying the per-tenant gateway token (`Authorization: Bearer`). The device private key is held server-side by the platform backend (fetched as KMS ciphertext from the control plane, then decrypted locally with `kms:Decrypt`); the public key is cold-injected into the microVM as a pairing file (`paired.json`); `deviceId = SHA256(raw 32-byte public key)`.

The gateway token and the device private key are both stored under AWS KMS envelope encryption (with `EncryptionContext` bound to `tenant_id` and `owner_id` respectively); the ciphertext is delivered to the caller via `GET /tenants/{id}`, and the caller decrypts it locally with `kms:Decrypt`; the plaintext never lands on host disk, never enters a command line, and never enters AWS CloudTrail.

The OpenResty edge performs no business authorization itself, only tenant routing: it looks up `{host, port, guest_ip}` in the Redis routing table by `tenant_id`, strips the `/ws/{tenant_id}` prefix, and forwards to the microVM gateway (the gateway does not accept prefixed URIs); the real identity verification is completed at the microVM gateway. The routing table is written into Redis by the host agent after the VM passes its liveness probe (`route:{tenant_id}`, no TTL, explicitly `DEL`ed on delete/migrate); the edge reads it through a three-tier cache (worker-local lrucache → shared dictionary → Redis) and fail-static serves the last known value during an ElastiCache failover window.

> **Note (media path pending redesign)**
>
> The earlier image upload/download (media) path, in which claw-hub co-signed Amazon S3 presigned URLs, went away with claw-hub; the media path under the two-tier routing model has not yet been re-implemented (the `finance-agent` demo sample shipped with the repository has no image scenario). Session history replay, which relied on hub WS history frames, is likewise no longer available and awaits redesign.

## Tenant microVM (OpenClaw agent runtime)

This section describes the disk architecture, identity injection method, and network addressing model of a tenant microVM. Each tenant runs inside an independent-kernel Firecracker microVM, elevating "privilege escalation stops at a single tenant" from the container level to the VM level; the microVM runs an OpenClaw agent, and identity, skills, and guardrails are cold-injected before startup. Firecracker is an AWS open-source lightweight microVM virtualization technology that runs on top of KVM, with low startup overhead and strong isolation. The pure microVM startup is about 1.74s (metal-measured, p50), and launch→gateway availability is about 6.48s (metal-measured).

### Disk architecture

A Firecracker microVM mounts four to five disks, assigned `/dev/vd<N>` in Firecracker PUT order, with root fixed as `vda`; all disks use ext4 as their file system:

- **rootfs (vda)**: `is_read_only:true` + `is_root_device:true`, the read-only root.
- **overlay (vdb)**: `is_read_only:false`, the per-VM copy-on-write layer.
- **data (vdc)**: `is_read_only:false`, carrying tenant configuration and skills.
- **immutable (vdd)**: `is_read_only:true`, the authoritative disk for identity and skills, carrying the identity files and operations skills; by default, if missing, an alert is raised and it is skipped (degraded state: the guest falls back to the stale identity copy baked into the data disk on build day, with no control-plane alert). Since #517 you can set `security.immutable_disk_required: true` to fail closed instead — when the disk is missing, `launch-vm.sh` exits 1, preferring the microVM not to boot over silently running the wrong identity (takes effect on rebuild after a deploy-code change, not a hot patch). The immutable disk must be PUT after data to ensure the guest sees it as `/dev/vdd` (Firecracker's disk-letter ordering constraint).
- **creds (vde, conditionally mounted)**: `is_read_only:true`, mounted only when the tenant carries injected credentials (`injected_credentials`), holding the decrypted dotenv (`.env`), ro-bind mounted into `~/.openclaw/.env`. Tenants without injected credentials still have four disks.

Read-only semantics do not depend on a special read-only file system, but are guaranteed by three layers stacked together: ① Firecracker sets a write barrier at the virtio-block layer with `is_read_only:true`, so that even a write as root inside the guest is blocked at the underlying level; ② after the guest boots, it mounts with `mount -o ro /dev/vdd`; ③ `openclaw-ro-harden` bind-overlays the identity files and guardrail code as read-only. With these three layers stacked, writing to identity files or operations skills as root is rejected (Read-only file system).

### Identity cold injection

Identity, skills, and configuration follow "cold injection before startup": identity files and operations skills are baked into the read-only immutable disk; tenant-specific configuration (gateway token, device pairing file `paired.json`, per-tenant billing vkey) is injected into `openclaw.json` on the data disk and the pairing file before startup. The VM is a finished product at startup, and the control plane performs no behavioral or data injection into the running VM. Modifying a tenant's identity requires rebuilding the image and rebuilding, rather than calling a runtime API.

Data-plane identity uses OpenClaw's native device asymmetric authentication: when a tenant is registered, the control plane mints an Ed25519 device key pair and a gateway token with AWS KMS; both the private key and the token are stored under KMS envelope encryption in the `openclaw-tenant-secrets` table. When the VM starts, the deployment script assembles the device public key into `paired.json` (per openclaw 2026.2.26 protocol v3: `roles` includes operator, and a matching public key passes the pairing gate) and cold-injects it onto the disk, and the gateway token ciphertext is KMS-decrypted and written into `.gateway.auth.token` in `openclaw.json`. The private key and token plaintext are never baked into the read-only golden image and never delivered to the browser.

### Network addressing model

Network addressing uses a dedicated /30 point-to-point link per VM (4 addresses: network, host end, guest end, broadcast). Addresses are computed by the launch-vm startup script from `vm_num`: `block=(vm_num-1)*4`, with the host-end IP being `SUBNET_PREFIX.<o3>.<base+1>` and the guest end being `SUBNET_PREFIX.<o3>.<base+2>`. All links fall within the tenant supernet `SUBNET_PREFIX/16` (production uses the real `172.16`; documentation uses the placeholder `10.0`), so an east-west DROP rule that applies to the /16 covers every VM. The MAC encodes `vm_num` into its last two bytes, supporting hundreds of VMs per host without collision. Each host is managed by an Amazon EC2 Auto Scaling group (ASG) for elastic scaling and idle reclamation, using metal-series instance types; a single metal instance (r8g.metal-24xl) is estimated at about 380 tenants/host by 760GB÷2GB (estimated), while a single metal instance fully healthy is measured at 187 nodes (disk bottleneck, not a memory ceiling — measured). A blank VM RSS is about 609MB, with a whole-machine average of about 669MB (measured).

## Defense in depth: the five-layer security model

This section describes the defense-in-depth security model of this solution. The model is composed of five stacked layers, each landed in code or on AWS devices rather than relying on model self-discipline: L1 content layer (Amazon Bedrock Guardrails), L2 tool execution layer (sentinel-guard / acl-guard), L3 identity layer (OpenClaw native device authentication + control-plane RBAC + owner gating), L4 network layer (three classes of iptables DROP + default-deny egress allowlist), and L5 credentials, read-only, and monitoring layer. Physical and network isolation govern "between tenants", while the tool execution layer and content layer govern "what an agent can do after being induced or injected".

### L1 content layer (Amazon Bedrock Guardrails)

This layer governs the language content going into and out of the large language model itself. Before user input reaches the model and before the model output returns to the user, Amazon Bedrock Guardrails — an AWS-managed content guardrail — passes it through once: identifying and rejecting jailbreaks and high-risk intent, filtering harmful content by predefined categories, redacting various credentials and sensitive strings, and specifically identifying injection and social-engineering phrasing in Chinese-language scenarios. This layer runs on the AWS platform side, decoupled from the agent process, and is the outermost layer of defense in depth. Jailbreak testing was executed item by item against the OWASP LLM Top 10 corpus: all 14 attacks blocked, 14/14; the 4 normal controls had zero false positives, 4/4 (measured). The Guardrail resource identifiers (ID/ARN) are deployment-state values and are represented by placeholders in this guide.

### L2 tool execution layer (sentinel-guard / acl-guard)

This layer is nailed in place just before an agent actually executes an action; it does not look at what the agent "wants" to do, only at the concrete command the agent is "about to execute", the file it is about to read, and the address it is about to access. Anything falling into a dangerous pattern is blocked before execution, using fail-closed (when in doubt, block). This layer is composed of two intentionally independent backends, both baked into the read-only image and running inside the agent process:

- **sentinel-guard**: Covers multiple threat classes including credential theft, data exfiltration, destructive commands, reverse shells, privilege escalation, mandatory confirmation for fund operations, forged internal requests (SSRF), identity tampering, sensitive information redaction, prompt injection and malicious-skill screening, and anomalous behavior monitoring. Among these, mandatory confirmation for fund operations is a hard veto before execution: any withdrawal, transfer, or real order-placement operation must explicitly carry a "dry-run/preview/confirmation token" marker to be allowed; otherwise it is rejected, and this is not staked on prompt constraints.
- **acl-guard**: A credential backstop layer that runs before sentinel-guard, matching by path or target rather than by command name, locking down references to SSH private keys, AWS credential files, process environment-variable secrets, and cloud metadata credential interfaces, and covering side channels the command layer might miss (for example, reading the same private key file with uncommon tools such as awk, dd, or base64).

The tool execution layer guardrails ship with their own regression tests. The authoritative external numbers: targeted cases against malicious skills, 41/41 all blocked; targeted cases for the credential backstop guardrail, 8/8 all hit (measured). Both backends are fail-closed and maintain blocking even if logging cannot be written, never allowing a request through because of a logging failure.

### L3 identity layer (device authentication + control-plane RBAC + owner gating)

This layer divides into two planes. The **data plane** roots identity in OpenClaw's native Ed25519 device asymmetric authentication: the platform backend signs the challenge issued by the gateway with the device private key, the microVM gateway verifies the signature with the cold-injected public key, and the pairing gate admits only the public keys and roles registered in `paired.json`; the private key is held server-side and never reaches the front end, and the KMS `EncryptionContext` of the token and private-key ciphertexts is bound to `tenant_id`/`owner_id`, so a mismatched decryption context is rejected (fail-closed). The data plane is structurally non-cross-tenant: one device binds to one tenant, the edge routes on the single `tenant_id` key, and a missing route returns 404 rather than crossing over to another tenant.

The **control plane** requires `x-api-key` as a usage-plan client identifier, not as standalone authentication, and layers Amazon Cognito verification when RBAC is enabled. Cognito tokens are verified with RS256 and JWKS; `cognito:groups` maps to viewer/operator/admin. A request without a Bearer uses `DEFAULT_NO_JWT_ROLE` (default `viewer`). RBAC is enabled by default, while owner and platform-scope checks are independent.

> **Note**
>
> In the current deployment code, Amazon Cognito is used only for control-plane console login (`console_auth.enabled` defaults to `false`, and the whole section is dormant); it is not on the chat data-plane path. The data plane's earlier three Cognito identities (a User Pool + two app clients + `custom:tenant_user_id`) went away together with claw-hub.

### L4 network layer (three classes of iptables DROP + default-deny egress allowlist)

This layer enforces cross-tenant and cross-boundary network isolation on the host with iptables (Firecracker itself does not filter traffic; egress filtering relies entirely on host iptables). All security DROPs are inserted at the top of the chain to ensure they precede any appended ACCEPT/MASQUERADE. The three classes of DROP are: ① IMDS isolation, DROP in the FORWARD chain of guest traffic to `169.254.169.254` and `169.254.169.253`, preventing a tenant from reaching the host's instance metadata service through MASQUERADE to steal the host EC2 instance-profile credentials; ② east-west L2 isolation, DROP in the FORWARD chain of guest traffic to the entire tenant supernet `SUBNET_PREFIX/16`, preventing a packet from being routed into another tenant's /30; ③ management-plane isolation, DROP in the INPUT chain of guest traffic to the host's ports 8899/9090/22.

Egress supports a default-deny allowlist (config-gated `security.egress_allowlist_enabled`, defaults to false; before enabling, guest egress is unrestricted and behavior is unchanged). Once enabled, the unconditional ACCEPT at the tail of the FORWARD chain is replaced by: allow the VPC CIDR and operator-supplied custom CIDRs (covering private targets such as LiteLLM, the edge, and VPC Endpoints), allow the real IPs that host dnsmasq resolves for allowlisted domains (built-ins such as `s3.{region}.amazonaws.com`; operators may add domains such as exchange market-data APIs), and append a tail DROP for that tenant's traffic to the public interface. The domain allowlist is implemented via host dnsmasq: `nat/PREROUTING` transparently DNATs the guest's port 53 to host dnsmasq, which populates an ipset with the IPs of matched domains as it resolves them, and the FORWARD chain allows them via `-m set --match-set` — so the guest image is not modified (guest DNS stays unchanged) yet egress is still confined. `cognito-idp` is allowed by domain rather than by IP range because AWS `ip-ranges.json` does not publish a dedicated address range for Cognito (it falls only within the broad AMAZON aggregate).

Note: Amazon Route 53 Resolver DNS Firewall (config-gated `security.dns_firewall_enabled`, defaults to false) acts on DNS queries that traverse the VPC Route 53 Resolver; because the microVM guest DNS does not traverse the VPC Resolver, DNS Firewall is positioned as an out-of-band / VPC-layer blocklist for C2 and data-exfiltration domains, orthogonal to the tap-level egress allowlist above and not a substitute for it. Confining microVM egress relies on the egress allowlist.

The core numbers for cross-tenant isolation: 100% packet loss east-west after hardening (post-hardening target state; the hardening code has landed and is confirmed by static rules, with a fresh bare-metal re-test to be verified); in the vulnerable state (no FORWARD DROP), cross-tenant traffic is fully interconnected, 0% packet loss, RTT 0.187ms (measured). IMDS returns 401 at the IMDSv2 application layer when no token is present.

> **Note**
>
> IMDS DROP currently covers only IPv4 (`169.254.169.254`/`.253`); ip6tables protection for IMDSv6 (`fd00:ec2::254`) has not yet landed.

### L5 credentials, read-only, and monitoring layer

This layer covers credential minimization, image immutability, and runtime monitoring. No long-lived AWS credentials reside inside the guest (zero-credential golden image); the gateway token and the device private key are stored under AWS KMS envelope encryption, with ciphertext delivered on demand and decrypted locally by the caller (see "Data plane" in this section); the master key of the per-tenant billing vkey resides only in AWS Secrets Manager, read once on demand at Lambda cold start and cached, never entering env in plaintext and never delivered to host or guest, with the Lambda role's `secretsmanager:GetSecretValue` permission scoped to a single secret prefix. IMDSv2 is enforced on the host side (`HttpTokens=required` + `HttpPutResponseHopLimit=1`). Image immutability is guaranteed by the write-barrier semantics of the read-only disks (see "Tenant microVM" in this section). At host startup, three cross-tenant side channels and data-residue surfaces are explicitly disabled: KSM (kernel same-page merging), SMT (hyper-threading), and swap; the hardening is inherited across rebuilds, auditable, and idempotent. Runtime monitoring includes in-guest auditd (overhead about 11.7MB, measured) and Wazuh file integrity monitoring (FIM, about 42MB, measured) — in-guest runtime threat monitoring is carried by Wazuh/auditd and does not rely on the Amazon GuardDuty Runtime agent (which is not enabled in this stack). On the AWS platform side, additional baseline controls are layered on: Amazon GuardDuty account-level threat detection (VPC/DNS/EC2/S3 and other cloud-layer findings, config-gated, with `RUNTIME_MONITORING` off by default), Amazon S3 whole-bucket public-access block + enforced HTTPS, and VPC Flow Logs (config-gated, defaults to true, delivered to Amazon CloudWatch for network forensics).

Audit responsibilities are separated by "who records it, is it immutable, and how long is it retained". Tenant business-data backups are stored in an Amazon S3 bucket that, in the data-retention region (`ap-southeast-1`), enables Object Lock (COMPLIANCE mode) + Versioning for WORM semantics: within the retention window not even the root account can overwrite or delete an object version or shorten the retention period; the implementation is in `deploy/stacks/storage.py` (the gate is decided by the retention-region check). Control-plane API-change auditing writes to an Amazon DynamoDB audit table (`GET /audit-log`) on a best-effort append basis, with a 90-day TTL; it is a mutable audit trail rather than WORM, and is not suitable as immutable compliance evidence. A truly immutable audit trail aligned with SEC 17a-4 / CFTC / FINRA (Object-Lock-protected AWS CloudTrail plus multi-region integrity validation) is currently planned (not implemented, tracked as issue #32); today AWS CloudTrail reuses the account-level trail with log-file validation only, without Object Lock, and must not be presented as a shipped capability.
