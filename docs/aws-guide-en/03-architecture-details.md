# Architecture details

This section describes the components and AWS services that make up this solution, along with details of how these components work together. The solution comprises three major components: a control plane (lifecycle management plane) responsible for registration, lifecycle, backup, and deregistration; a data plane (the real-time chat hub, claw-hub) that routes real-time chat requests per tenant; and tenant microVMs (independent-kernel runtimes based on Firecracker) that run an OpenClaw AI agent with identity, skills, and guardrails for each tenant. The three responsibilities are orthogonal: the control plane performs lifecycle management only and injects no business data into a microVM after startup; the data plane performs per-tenant message routing only; and the tenant microVM is an isolated runtime that is a finished product at startup. The security model is layered on top of these three components as five layers of defense in depth, described in "Defense in depth: the five-layer security model" in this section.

## Control plane (lifecycle management plane)

This section describes the component composition and responsibility boundaries of the control plane. This component is built from AWS Lambda, Amazon DynamoDB, and Amazon API Gateway, is deployed through the AWS Cloud Development Kit (AWS CDK), and is responsible for tenant registration, start/stop, backup, migration, and deregistration. It does not participate in the real-time chat path.

The control plane exposes a set of REST APIs, all fronted by Amazon API Gateway and requiring `x-api-key`, backed by a single AWS Lambda function that serves endpoints for tenant registration, lifecycle operations, backup, host/skill/group management, and audit logging. Control plane state is persisted in Amazon DynamoDB, with three core state tables organized by responsibility as follows (plus an audit table and operational/federation helper tables such as batch-jobs and tenant-idp-map):

- **tenants table**: A schemaless table keyed on `id`, writing fields such as `owner_id`, `tenant_user_id`, `authorized_users`, `litellm_vkey`, and `channel_secret` on demand, carrying tenant metadata and authorization records. There is no complete table-level schema to reference.
- **hosts table**: Records host node status, specifications, and capacity counts (accounting for the overcommit ratio, available capacity = (total × ratio) − used).
- **groups table**: Records the skill set for each group, used to resolve a tenant's effective skills by group.

The control plane follows the "zero runtime operations" discipline: after a microVM starts, the control plane performs no behavioral or data injection into the running VM, and the host performs only lifecycle, resource, and network management. Modifying tenant identity, skills, or configuration requires rebuilding the image and performing a rolling rebuild, rather than calling a runtime API. Identity, skills, credentials, and configuration are cold-injected into the read-only golden image disk and data disk before the VM starts, and no bulk hot-injection channel from host to VM is opened after startup.

A control plane registration request defines the startup parameters for each VM: `tenant_id`, `vm_num`, along with `vcpu` (script default 2) and `mem_mb` (script default 4096).

> **Note**
>
> The `vcpu` default of 2 and `mem_mb` default of 4096 are startup-script defaults and differ from the steady-state capacity estimated at 2 GB/VM (the defaults are larger). The capacity descriptions in this guide consistently use the 2 GB/VM basis.

The control plane lifecycle operations have measured data with time anchors: the registration API returns in about 1.7s, creating→running availability is about 4.0s, hibernation (stop→stopped) about 6.0s, wakeup (start→running) about 3.7s, backup about 6.6s (artifact about 9.5MB), deregistration (DELETE→deleted) about 12.2s, and backup restore about 16s (9MB backup) — all lifecycle-measured.

Data protection for the control plane tables and protection for tenant business data are two independent mechanisms: the four `RETAIN` tables (tenants, hosts, groups, and audit) all have Point-in-Time Recovery (PITR) enabled (35 days of continuous backup by default, recoverable to any point within the recovery window), preventing control plane metadata from being unrecoverable after accidental deletion, modification, or corrupted writes; tenant business data, by contrast, is delivered by the backup Lambda to an Amazon S3 bucket with Object Lock (COMPLIANCE) enabled. PITR is config-gated (`dynamodb.point_in_time_recovery` defaults to true), on by default in code and inherited across rebuilds.

> **Note**
>
> Customer managed key (CMK) encryption for the Amazon DynamoDB audit table is currently planned (not implemented). The existing tables are `RETAIN`, and switching encryption online would force a replace and lose audit data, so it is planned only when a brand-new account is first deployed.

## Data plane (real-time chat hub, claw-hub)

This section describes the connection model and signature verification planes of the data plane. This component is a self-built WebSocket hub (claw-hub) that routes chat requests from browsers or front ends to the corresponding OpenClaw agent inside each tenant's microVM, and performs explicit application-layer authorization for cross-tenant access.

The data plane adopts an outbound-WS hub model: the `claw-channel` inside each microVM proactively dials out to claw-hub and opens no inbound ports. Real-time delivery between the browser and the agent is entirely forwarded over claw-hub's WebSocket, along the path "browser ↔ claw-hub ↔ claw-channel inside the microVM ↔ agent". The sole public entry point is through Amazon CloudFront → Application Load Balancer; CloudFront's `/hub/*` behavior forwards all request headers (including `Upgrade` and `Sec-WebSocket-*`), disables caching, allows all methods, and sets the origin read timeout to 60s to sustain long-lived WebSocket connections.

The data plane distinguishes three types of token corresponding to two independent signature verification planes; the trust of all three tokens ultimately traces back to Amazon Cognito:

- **Control plane Cognito id_token**: Carried in `Authorization: Bearer` when calling the control plane REST API, verified with RS256 against Amazon Cognito's JWKS public key, with issuer validation; verification failure always degrades to the least privilege (viewer).
- **Chat front-end token**: Required for a browser to connect to claw-hub's WebSocket. The client initiates through `POST /token` (with the Cognito id_token Bearer and `tenant_id`); claw-hub first verifies with RS256 against Amazon Cognito's JWKS, then performs an explicit tenant authorization check (whether the user is the tenant owner or an authorized user), and only then issues the token. This token is an HMAC token self-signed by claw-hub, TTL 300s, carrying five claims: `role` (fixed as `frontend`), `sub` (the server-verified user identity), `tenant`, `access`, and `exp`.
- **Chat channel token**: Required for the claw-channel inside a microVM to register an outbound connection with claw-hub. The channel initiates through `POST /channel-token` (with `tenant_id`, `appId`, `timestamp`, and `signature`, where the signature is `HMAC-SHA256("{appId}:{timestamp}", appSecret)`, a ±300s time window, and constant-time comparison). The channel token carries only three claims — `role` (`channel`), `tenant`, and `exp` — and no `sub`, because it represents a tenant rather than a specific user.

The two signature verification planes are orthogonal: the control plane plane uses the Cognito id_token Bearer plus RBAC; the chat plane internally divides into the front-end token and the channel token, each verified independently, but issuance of the front-end token is likewise predicated on Cognito id_token verification. Amazon Cognito is the single root of trust for authentication across the entire platform; both the control plane and the data plane accept only tokens issued and verified through Cognito. External accounts federated through OpenID Connect (OIDC) are also federated into the same Cognito user pool, after which Cognito re-issues the id_token — transparent to claw-hub and introducing no new credential on the guest side.

Image upload and download (media) paths are completed through Amazon S3 presigned URLs; claw-hub is the only component holding the S3 instance role, converging the blast radius of S3 access to a single place:

- **Image download (inbound)**: When a user uploads, the front end presigns a PUT to Amazon S3 through claw-hub and sends a FILE frame carrying the fileKey; claw-channel obtains a presigned GET, validates MIME type and size locally, and passes the content to the multimodal core.
- **Image upload (outbound)**: When the agent references a local file, claw-channel validates MIME type and size and uploads to Amazon S3 through a claw-hub presign, and the front end then obtains a presigned URL.

The file endpoints validate tenant ownership: when obtaining a download link, the tenant segment in the path must match the tenant in the token, and even whether a cross-tenant object exists is not disclosed. Cross-origin resource sharing (CORS) on the Amazon S3 media bucket allows only the single CloudFront domain.

> **Important**
>
> The `POST /chat/sign` endpoint and the three `x-claw-*` headers (signature/random/timestamp) are historical remnants of an early "signature → through nginx → VM inbound" design: claw-channel is an outbound-WS model that opens no inbound ports, and there is no corresponding inbound signature verifier anywhere in the code. Integrators should not treat these as an active contract; C-side chat delivery is in fact entirely completed over claw-hub's WebSocket path.

> **Note**
>
> claw-hub currently runs in production as a single-process metal form (brought up by systemd). The cross-Pod Redis routing (cluster-routing) code is complete and degrade-safe, but the Amazon Elastic Kubernetes Service (Amazon EKS) multi-replica gradual rollout has not yet been cut over to production (target state). The integration contract (`/hub/token`, `/hub/ws`, and frame structure) is identical in single-process and multi-replica modes.

## Tenant microVM (OpenClaw agent runtime)

This section describes the disk architecture, identity injection method, and network addressing model of a tenant microVM. Each tenant runs inside an independent-kernel Firecracker microVM, elevating "privilege escalation stops at a single tenant" from the container level to the VM level; the microVM runs an OpenClaw agent, and identity, skills, and guardrails are cold-injected before startup. Firecracker is an AWS open-source lightweight microVM virtualization technology that runs on top of KVM, with low startup overhead and strong isolation. The pure microVM startup is about 1.74s (metal-measured, p50), and launch→gateway availability is about 6.48s (metal-measured).

### Four-disk architecture

A Firecracker microVM mounts four disks, assigned `/dev/vd<N>` in Firecracker PUT order, with root fixed as `vda`; all four disks use ext4 as their file system:

- **rootfs (vda)**: `is_read_only:true` + `is_root_device:true`, the read-only root.
- **overlay (vdb)**: `is_read_only:false`, the per-VM copy-on-write layer.
- **data (vdc)**: `is_read_only:false`, carrying tenant configuration and skills.
- **immutable (vdd)**: `is_read_only:true`, the authoritative disk for identity and skills, carrying the identity files and operations skills; if missing, an alert is raised and it is skipped (degraded state). The immutable disk must be PUT after data to ensure the guest sees it as `/dev/vdd` (Firecracker's disk-letter ordering constraint).

Read-only semantics do not depend on a special read-only file system, but are guaranteed by three layers stacked together: ① Firecracker sets a write barrier at the virtio-block layer with `is_read_only:true`, so that even a write as root inside the guest is blocked at the underlying level; ② after the guest boots, it mounts with `mount -o ro /dev/vdd`; ③ `openclaw-ro-harden` bind-overlays the identity files and guardrail code as read-only. With these three layers stacked, writing to identity files or operations skills as root is rejected (Read-only file system).

### Identity cold injection

Identity, skills, and configuration follow "cold injection before startup": identity files and operations skills are baked into the read-only immutable disk; tenant-specific configuration (channel secret, per-tenant billing vkey) is injected into `openclaw.json` on the data disk before startup. The VM is a finished product at startup, and the control plane performs no behavioral or data injection into the running VM. Modifying a tenant's identity requires rebuilding the image and rebuilding, rather than calling a runtime API. The HMAC channel secret adopts a control-plane pre-generation model: when a tenant is registered, the control plane mints it from a 32-byte random value, writes it into the DynamoDB record, and injects it into the data disk through the deployment script when the VM starts, so that claw-hub can verify the channel's first registration; this secret is never baked into the read-only golden image and never delivered to the browser.

### Network addressing model

Network addressing uses a dedicated /30 point-to-point link per VM (4 addresses: network, host end, guest end, broadcast). Addresses are computed by the launch-vm startup script from `vm_num`: `block=(vm_num-1)*4`, with the host-end IP being `SUBNET_PREFIX.<o3>.<base+1>` and the guest end being `SUBNET_PREFIX.<o3>.<base+2>`. All links fall within the tenant supernet `SUBNET_PREFIX/16` (production uses the real `172.16`; documentation uses the placeholder `10.0`), so an east-west DROP rule that applies to the /16 covers every VM. The MAC encodes `vm_num` into its last two bytes, supporting hundreds of VMs per host without collision. Each host is managed by an Amazon EC2 Auto Scaling group (ASG) for elastic scaling and idle reclamation, using metal-series instance types; a single metal instance (r8g.metal-24xl) is estimated at about 380 tenants/host by 760GB÷2GB (estimated), while a single metal instance fully healthy is measured at 187 nodes (disk bottleneck, not a memory ceiling — measured). A blank VM RSS is about 609MB, with a whole-machine average of about 669MB (measured).

## Defense in depth: the five-layer security model

This section describes the defense-in-depth security model of this solution. The model is composed of five stacked layers, each landed in code or on AWS devices rather than relying on model self-discipline: L1 content layer (Amazon Bedrock Guardrails), L2 tool execution layer (sentinel-guard / acl-guard), L3 identity layer (Amazon Cognito + RBAC + owner gating), L4 network layer (three classes of iptables DROP + DNS Firewall), and L5 credentials, read-only, and monitoring layer. Physical and network isolation govern "between tenants", while the tool execution layer and content layer govern "what an agent can do after being induced or injected".

### L1 content layer (Amazon Bedrock Guardrails)

This layer governs the language content going into and out of the large language model itself. Before user input reaches the model and before the model output returns to the user, Amazon Bedrock Guardrails — an AWS-managed content guardrail — passes it through once: identifying and rejecting jailbreaks and high-risk intent, filtering harmful content by predefined categories, redacting various credentials and sensitive strings, and specifically identifying injection and social-engineering phrasing in Chinese-language scenarios. This layer runs on the AWS platform side, decoupled from the agent process, and is the outermost layer of defense in depth. Jailbreak testing was executed item by item against the OWASP LLM Top 10 corpus: all 14 attacks blocked, 14/14; the 4 normal controls had zero false positives, 4/4 (measured). The Guardrail resource identifiers (ID/ARN) are deployment-state values and are represented by placeholders in this guide.

### L2 tool execution layer (sentinel-guard / acl-guard)

This layer is nailed in place just before an agent actually executes an action; it does not look at what the agent "wants" to do, only at the concrete command the agent is "about to execute", the file it is about to read, and the address it is about to access. Anything falling into a dangerous pattern is blocked before execution, using fail-closed (when in doubt, block). This layer is composed of two intentionally independent backends, both baked into the read-only image and running inside the agent process:

- **sentinel-guard**: Covers multiple threat classes including credential theft, data exfiltration, destructive commands, reverse shells, privilege escalation, mandatory confirmation for fund operations, forged internal requests (SSRF), identity tampering, sensitive information redaction, prompt injection and malicious-skill screening, and anomalous behavior monitoring. Among these, mandatory confirmation for fund operations is a hard veto before execution: any withdrawal, transfer, or real order-placement operation must explicitly carry a "dry-run/preview/confirmation token" marker to be allowed; otherwise it is rejected, and this is not staked on prompt constraints.
- **acl-guard**: A credential backstop layer that runs before sentinel-guard, matching by path or target rather than by command name, locking down references to SSH private keys, AWS credential files, process environment-variable secrets, and cloud metadata credential interfaces, and covering side channels the command layer might miss (for example, reading the same private key file with uncommon tools such as awk, dd, or base64).

The tool execution layer guardrails ship with their own regression tests. The authoritative external numbers: targeted cases against malicious skills, 41/41 all blocked; targeted cases for the credential backstop guardrail, 8/8 all hit (measured). Both backends are fail-closed and maintain blocking even if logging cannot be written, never allowing a request through because of a logging failure.

### L3 identity layer (Amazon Cognito + RBAC + owner gating)

This layer uses Amazon Cognito as the single root of trust for authentication and authorization. The control plane API verifies Cognito-issued tokens with RS256 + the JWKS public key, and verification failure always degrades to the least privilege (viewer), never defaulting to admin; the `cognito:groups` claim maps to the three-tier roles viewer/operator/admin, and forged, expired, `alg:none`, or wrong-issuer tokens all degrade to read-only. Role-based access control (RBAC) gating is itself an independent switch, `RBAC_ENABLED`, defaulting to `true` (per-route role checks plus owner checks enforced by default). The data plane claw-hub writes "a token bound to one tenant + a channel registered to one tenant + no cross-bridge matching" into identifiable authorization points: `authorizeSubForTenant` decides based on `owner_id` and `authorized_users`, rejecting on DDB error (fail-closed) and rejecting another user's private node (`not-authorized`). Cross-tenant access on the chat path is structurally blocked: the front-end token carries only one tenant, the channel registers only one tenant, and the hub requires the two to match when routing; otherwise it routes to an empty channel.

> **Note**
>
> Shared access to a "no explicit owner" node (`owner_id` being `api-key` or empty) is gated by `CLAW_HUB_SHARED_TENANT_ACCESS`, off by default; when off, such nodes are always rejected for front-end users (fail-closed). RBAC being on by default is the exception among the config-gated capabilities.

### L4 network layer (three classes of iptables DROP + DNS Firewall)

This layer enforces cross-tenant and cross-boundary network isolation on the host with iptables (Firecracker itself does not filter traffic). All security DROPs are inserted at the top of the chain to ensure they precede any appended ACCEPT/MASQUERADE. The three classes of DROP are: ① IMDS isolation, DROP in the FORWARD chain of guest traffic to `169.254.169.254` and `169.254.169.253`, preventing a tenant from reaching the host's instance metadata service through MASQUERADE to steal the host EC2 instance-profile credentials; ② east-west L2 isolation, DROP in the FORWARD chain of guest traffic to the entire tenant supernet `SUBNET_PREFIX/16`, preventing a packet from being routed into another tenant's /30; ③ management-plane isolation, DROP in the INPUT chain of guest traffic to the host's ports 8899/9090/22. Outbound DNS interception is provided by Amazon Route 53 Resolver DNS Firewall as an L4 egress supplement: at the DNS resolution layer, it BLOCKs known C2 and data-exfiltration domains, so that a guest resolving such domains directly receives NXDOMAIN. This layer is config-gated (`security.dns_firewall_enabled`, defaults to false), and the actual threat-intelligence domain lists are security-sensitive data that do not enter the repository; in production, operations load them from a controlled source separately.

The core numbers for cross-tenant isolation: 100% packet loss east-west after hardening (post-hardening target state; the hardening code has landed and is confirmed by static rules, with a fresh bare-metal re-test to be verified); in the vulnerable state (no FORWARD DROP), cross-tenant traffic is fully interconnected, 0% packet loss, RTT 0.187ms (measured). IMDS returns 401 at the IMDSv2 application layer when no token is present.

> **Note**
>
> IMDS DROP currently covers only IPv4 (`169.254.169.254`/`.253`); ip6tables protection for IMDSv6 (`fd00:ec2::254`) has not yet landed.

### L5 credentials, read-only, and monitoring layer

This layer covers credential minimization, image immutability, and runtime monitoring. No long-lived AWS credentials reside inside the guest (zero-credential golden image); when read/write access to Amazon S3 is needed, claw-hub co-signs the presigned URL; the master key of the per-tenant billing vkey resides only in AWS Secrets Manager, read once on demand at Lambda cold start and cached, never entering env in plaintext and never delivered to host or guest, with the Lambda role's `secretsmanager:GetSecretValue` permission scoped to a single secret prefix. IMDSv2 is enforced on the host side (`HttpTokens=required` + `HttpPutResponseHopLimit=1`). Image immutability is guaranteed by the read-only semantics of the four disks (see "Tenant microVM" in this section). At host startup, three cross-tenant side channels and data-residue surfaces are explicitly disabled: KSM (kernel same-page merging), SMT (hyper-threading), and swap; the hardening is inherited across rebuilds, auditable, and idempotent. Runtime monitoring includes in-guest auditd (overhead about 11.7MB, measured) and Wazuh file integrity monitoring (FIM, about 42MB, measured) — in-guest runtime threat monitoring is carried by Wazuh/auditd and does not rely on the Amazon GuardDuty Runtime agent (which is not enabled in this stack). On the AWS platform side, additional baseline controls are layered on: Amazon GuardDuty account-level threat detection (VPC/DNS/EC2/S3 and other cloud-layer findings, config-gated, with `RUNTIME_MONITORING` off by default), Amazon S3 whole-bucket public-access block + enforced HTTPS, and VPC Flow Logs (config-gated, defaults to true, delivered to Amazon CloudWatch for network forensics).
