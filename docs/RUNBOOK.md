## 1. Architecture at a glance

**Control plane** — API Gateway (`openclaw-orchestrator`, stage `v1`, `x-api-key` auth) → `openclaw-api` Lambda → DynamoDB. **Data plane** — EC2 Auto Scaling Group `openclaw-hosts-asg` of Firecracker hosts; each runs `host-agent.py` (systemd, 15 s poll loop) plus per-tenant microVMs. Tenant dashboards route CloudFront → ALB → host Nginx → VM:18789. Web console served from S3 via CloudFront at `/console/`.

### Lambdas & schedules

| Function | Trigger | Does |
|---|---|---|
| `openclaw-api` | API Gateway + ASG EventBridge rules (`HostReadyRule`, `HostTerminateRule`) | Tenant/host CRUD, migrate, drain, failover trigger, pending-tenant assignment, host teardown cleanup |
| `openclaw-health-check` | EventBridge rate, every `health_check.interval_minutes` (default **5 min**); `reserved_concurrent_executions=1` | Staleness watchdog, host-agent restart, AZ failover, in-flight migration sweep + 15-min watchdog |
| `openclaw-scaler` | EventBridge rate, every `scaler.interval_minutes` (default **3 min**) | Idle-host reclaim (two-round), TTL expiry, office-hours schedules |
| `openclaw-backup` | EventBridge cron `s3.backup_cron` (default `cron(0 19 * * ? *)` = UTC 19:00 daily) + async invoke from API | Pause→pigz→S3→resume backup of running tenants' data volumes |
| `openclaw-skills` / `openclaw-templates` | API Gateway | Shared-skills listing / config-template CRUD |

### DynamoDB tables

| Table | Key | Holds | Protection |
|---|---|---|---|
| `openclaw-tenants` | `id` | Tenant records: `status`, `host_id`, `vm_num`, `vcpu`, `mem_mb`, `last_health_check`, `migration_*` fields | PITR + deletion protection + RETAIN |
| `openclaw-hosts` | `instance_id` | Host capacity/status: `az`, `total_vcpu`, `used_vcpu`, `vm_count`, `last_seen`, `last_health_check`; synthetic row `__az_failover_state__` holds per-AZ cooldowns | PITR + deletion protection + RETAIN |
| `openclaw-groups` | `name` | Skill groups | PITR + deletion protection + RETAIN |
| `openclaw-audit-log-<suffix>` | `pk="audit"` + `ts` | 90-day-TTL audit trail (query via `GET /audit-log`) | PITR + RETAIN (no deletion protection — by design) |

## 2. Deploy & rollback

### Full deploy / upgrade

```bash
uv sync                                   # deps into .venv (CDK imports aws-cdk-lib from here)
./setup.sh <region> [profile]             # CDK deploy + S3 script upload + console upload + .env.deploy
```

`setup.sh` = `cdk deploy -c region=… --require-approval never`, then uploads `deploy/userdata/*.sh` + `host-agent.py` to `s3://$ASSETS_BUCKET/deployment/scripts/`, regenerates `console/config.js`, and syncs the console. Docker is required (the api Lambda bundles `cryptography` for ARM64).

A redeploy **never touches running hosts or tenants** — the ASG has no rolling UpdatePolicy. Boot-path (`init-host.sh`) changes only reach *replaced* hosts; host-side scripts reach running hosts only via explicit push (below).

### Redeploy a single piece

```bash
# Lambda code only — cdk deploy diffs and updates just the changed function(s):
./setup.sh <region> [profile]

# Host-side script to RUNNING hosts (setup.sh only uploads for new boots):
aws s3 cp deploy/userdata/launch-vm.sh "s3://${ASSETS_BUCKET}/deployment/scripts/launch-vm.sh"
aws ssm send-command --document-name AWS-RunShellScript \
  --targets Key=tag:aws:autoscaling:groupName,Values=openclaw-hosts-asg \
  --parameters 'commands=["aws s3 cp s3://'${ASSETS_BUCKET}'/deployment/scripts/launch-vm.sh /home/ubuntu/launch-vm.sh","chmod +x /home/ubuntu/launch-vm.sh"]'

# New rootfs to all hosts (existing VMs pick it up on next reset):
curl -s -X POST "${API_URL}hosts/refresh-rootfs" -H "x-api-key: ${API_KEY}" | jq .
```

### Rollback

Control plane is fully declarative — roll back by deploying the previous ref:

```bash
git log --oneline -10                      # find last-good commit / tag
git checkout <last-good-ref>
uv sync && ./setup.sh <region> [profile]   # CDK converges Lambdas/API back
git checkout -                             # return the working tree
```

Data plane: rootfs versions are tracked in S3 `manifest.json`; re-run `./scripts/build-rootfs-on-ec2.sh <older-tag>` then `POST /hosts/refresh-rootfs` + per-tenant `reset` to roll VM images back. DynamoDB data is never touched by deploys (RETAIN + deletion protection); see [§6](#6-escalation--data-safety) for PITR.

### Tear down

```bash
./scripts/destroy.sh           # stack only; keeps S3 + DDB (RETAIN)
./scripts/destroy.sh --purge   # ⚠️ permanently deletes bucket + tenants/hosts tables — confirm prompt
```

### 2.1 `routing.mode: host-tg` — cutover gate (read before flipping)

`host-tg` replaces the per-tenant ALB listener rule (the ~499-tenant ceiling,
and an AWS *default* quota of 100 rules per ALB) with one shared target group +
a `/vm/*` catch-all + an nginx peer-map on every host. The data plane (P1) and
the flag (P2) are deployed; **the flag default is still `per-tenant` and
flipping it is not yet authorised.** Reasons, in order of severity:

**a. Rollback is currently a one-way door.** There is no code path that
rebuilds per-tenant rules for existing tenants — `_add_alb_rule` is only called
from `create_tenant` / `process_pending`, and while `host-tg` is active
`_ensure_host_tg` returns early so newly-registered hosts never get an
`oc-<last8>` target group at all. Flipping the config back and redeploying
restores the Lambda env var but **not** the ALB rule set, so the listener falls
through to its default `fixed_response 404` — 100% of tenants down. Past ~100
tenants (the default rule quota) per-tenant is not even a reachable state
without an AWS quota increase, which takes hours to days.

**b. The second hop had never carried a request.** The catch-all sits at
priority 999 while per-tenant rules occupy 1-499, and ALB matches lowest-first
— so the cross-host path was dead code in production despite being "deployed
and verified". It was also broken: the peer conf stripped the `/vm/<tid>`
prefix, which the owner host's `:8081` requires, so every cross-host request
would have 404'd. Fixed, plus a semantic regression test, but **still never
exercised against two real hosts.**

**c. Do NOT move the catch-all to priority 1.** It buys nothing (once the
per-tenant rules are gone, 999 and 1 are equivalent) and costs a lot: priority
1 is inside `_add_alb_rule`'s random pool, so a live tenant may hold it and the
deploy fails with `PriorityInUseException`; and the move is atomic and
fleet-wide, with no per-tenant canary.

**Gate — all of these before flipping the default:**

1. A real two-host `curl` through the second hop, including a WebSocket
   upgrade: `/vm/<tid>/` served by a host that does **not** own the tenant.
2. `openclaw_peer_map_last_success_age_seconds` < 2× `OC_ROUTE_SYNC_INTERVAL`
   on every host, and `openclaw_peer_map_reload_failures_total` flat at 0.
3. An ASG scale-out drill with zero 4xx on `/vm/*` — the shared target group
   health-checks `/ready` (not the always-200 `/health`) precisely so a host
   without peer routes stays out of service, and that needs to be observed.
4. A rebuild path for per-tenant rules exists and has been dry-run, so (a) is
   no longer a one-way door.
5. Gradual cutover instead of a flag flip: keep the catch-all at 999 and delete
   per-tenant rules **one tenant at a time**. Each deletion moves exactly that
   tenant onto the shared path, and rollback is recreating that one rule.

Record the current ALB rule count and tenant count before starting — together
they say whether the per-tenant fallback is still reachable at all.

## 3. Operator endpoints (T2-8)

All under `${API_URL}` with `-H "x-api-key: ${API_KEY}"`. With `console_auth.rbac_enabled: true`, writes additionally need a Cognito `Authorization: Bearer` token; **`POST /failover/{az}` requires the `admin` role** (the other two need `operator`).

### 3.1 Cancel an in-flight migration

```bash
curl -s -X POST "${API_URL}tenants/{id}/cancel-migration" -H "x-api-key: ${API_KEY}" | jq .
```

- **What it does**: valid only while `status=migrating`. The migrate sweep flips `host_id` only at the very last step, so until then the source VM is running and untouched — cancel reverts `status → running`, sets `migration_failed="cancelled by operator"`, and clears all `migration_*` fields. Returns `409` if the tenant is not `migrating` (if the sweep already flipped `host_id`, the migration completed; there is nothing to cancel).
- **When to use**: a migration is stuck (snapshot/restore SSM command hung, wrong target chosen) and you don't want to wait for the automatic **15-minute watchdog** (`MIGRATION_WATCHDOG_MINUTES`) in `openclaw-health-check` to roll it back for you. For cold-mode balloon migrations prefer letting the watchdog roll back — its `_rollback_migration` also **relaunches the stopped source VM**; the API cancel does not, so after cancelling a cold migration confirm the VM is up (and `POST /tenants/{id}/restart` if not).
- **Watch afterward**: `GET /tenants/{id}` → `status=running`, `migration_failed` populated, `host_id` unchanged; audit event `migration.cancelled` / `vm.migrate_cancelled` in `GET /audit-log`.

### 3.2 Drain a host (graceful decommission)

```bash
curl -s -X POST "${API_URL}hosts/{instance_id}/drain" -H "x-api-key: ${API_KEY}" | jq .
```

- **What it does**: marks the host `status=draining` (scheduler stops placing new tenants on it), then kicks off an **async migrate (202)** for every `running` tenant on it, each to the least-loaded host with capacity. Response lists `migrations_started` and `failed` (e.g. `"no target host with capacity"`).
- **When to use** vs alternatives: use drain before replacing/retiring a host (e.g. to pick up a new `init-host.sh`). **Do NOT use `DELETE /hosts/{id}` on a host that still has tenants** — it terminates immediately and the ASG lifecycle hook (`cleanup_terminated_host`) marks every tenant on it `deleted`.
- **Watch afterward**:
  ```bash
  # Poll until no running/migrating tenants remain on the host:
  curl -s "${API_URL}tenants" -H "x-api-key: ${API_KEY}" \
    | jq '[.[] | select(.host_id=="i-XXXX")] | map({id, status})'
  # Then — and only then — terminate:
  curl -s -X DELETE "${API_URL}hosts/i-XXXX" -H "x-api-key: ${API_KEY}" | jq .
  ```
  Migrations complete via the health-check sweep, so expect **one 5-min tick per phase** (snapshot → restore → verify). Any that fail roll back to `running` on the source with `migration_failed` set — retry with an explicit `POST /tenants/{id}/migrate` after fixing capacity.

### 3.3 Manual AZ failover

```bash
curl -s -X POST "${API_URL}failover/us-east-1a" -H "x-api-key: ${API_KEY}" | jq .
# → 202 {"az": "...", "status": "failover_triggered"}
```

- **What it does**: async-invokes the `openclaw-health-check` Lambda with `{"manual_failover_az": "<az>"}`. Since **T3-2** the detector honors that payload — it forces a synthetic outage for the named AZ **even if auto-detection wouldn't flag it** and **bypasses the 30-min per-AZ cooldown** (the operator asked explicitly). Each affected tenant is claimed, its target host + `vm_num` reserved, and one job enqueued to the `openclaw-failover` SQS queue; the `openclaw-failover-worker` Lambda then relaunches each tenant on a healthy host **from its latest backup**, re-points its ALB rule, and gates on a public-path dashboard probe before flipping DDB — **in parallel** (recovery is O(one tenant), not O(5min × tenant count)).
- **Verify it acted** (detector logs the queued count; workers do the recovery a beat later):
  ```bash
  aws logs tail /aws/lambda/openclaw-health-check --since 10m          # detector: "tenants_queued"
  aws logs tail /aws/lambda/openclaw-failover-worker --since 10m       # per-tenant execution
  curl -s "${API_URL}audit-log?limit=50" -H "x-api-key: ${API_KEY}" \
    | jq '.[] | select(.event | test("FAILOVER"))'  # AZ_FAILOVER_TENANT_QUEUED → ..._RECOVERED
  ```
- **When to use** vs waiting: auto-failover triggers only after **all** hosts in an AZ have been stale ≥ `unhealthy_threshold_minutes` (default 10). Use the manual endpoint when you already know the AZ is gone (AWS Health event) and don't want to wait. Fallback if the queue path isn't deployed (`FAILOVER_QUEUE_URL` unset, e.g. the Terraform path — see T3-6): the detector runs the legacy synchronous loop instead; evacuate host-by-host with `POST /hosts/{id}/drain` if the source host is still SSM-reachable.
- **Watch afterward**: affected tenants go `running → failover_queued → failover_recovering → running` with a new `host_id` and `restored_from` set to the backup key. Failure states: `failover_blocked` (no backup — see audit `AZ_FAILOVER_NO_BACKUP`; deliberate refusal to lose data), `failover_failed` (VM never verified on target, or the watchdog reaped a tenant stuck > `FAILOVER_WATCHDOG_MINUTES`=30), `failover_failed_partial` (VM up but ALB repoint/public probe failed — DDB still points at the source; fix ALB manually, see §5b). A job that exhausts its 2 retries lands in `openclaw-failover-dlq` (alarmed) — inspect like the EventsDLQ in §4.

## 4. Observability — alarms & DLQ

### CloudWatch alarms (T2-3)

All alarms fire to SNS: `openclaw-tenant-events` when `notifications.enabled: true`, else the fallback topic `openclaw-alarms`. Subscribe an email/Slack endpoint or you'll never see them:

```bash
TOPIC=$(aws sns list-topics --query "Topics[?contains(TopicArn,'openclaw')].TopicArn" --output text)
aws sns subscribe --topic-arn "$TOPIC" --protocol email --notification-endpoint you@example.com
```

| Alarm name | Metric | Threshold |
|---|---|---|
| `openclaw-api-errors` / `openclaw-api-throttles` | `openclaw-api` Lambda Errors / Throttles | ≥ 1 in 5 min |
| `openclaw-health-errors` / `openclaw-health-throttles` | `openclaw-health-check` Errors / Throttles | ≥ 1 in 5 min |
| `openclaw-scaler-errors` / `openclaw-scaler-throttles` | `openclaw-scaler` Errors / Throttles | ≥ 1 in 5 min |
| `openclaw-backup-errors` / `openclaw-backup-throttles` | `openclaw-backup` Errors / Throttles | ≥ 1 in 5 min |
| `openclaw-failoverworker-errors` / `openclaw-failoverworker-throttles` | `openclaw-failover-worker` Errors / Throttles (T3-2) | ≥ 1 in 5 min |
| `openclaw-events-dlq-not-empty` | `ApproximateNumberOfMessagesVisible` on the EventBridge DLQ | ≥ 1 in 5 min |
| `openclaw-failover-dlq-not-empty` | `ApproximateNumberOfMessagesVisible` on the failover DLQ (T3-2) — a tenant could not be recovered | ≥ 1 in 5 min |

```bash
aws cloudwatch describe-alarms --alarm-name-prefix openclaw \
  --query 'MetricAlarms[].{name:AlarmName,state:StateValue}' --output table
```

### EventsDLQ — inspect & redrive

SQS queue `openclaw-events-dlq` (14-day retention) catches EventBridge events that failed delivery after 2 retries: health/scaler/backup schedule ticks and — the ones that matter most — ASG **host-launch / host-terminate lifecycle events** targeted at `openclaw-api`. A lost terminate event = zombie host row + orphaned tenants; a lost launch event = pending tenants never assigned.

```bash
QURL=$(aws sqs get-queue-url --queue-name openclaw-events-dlq --query QueueUrl --output text)

# 1) Depth + peek (peek does NOT delete; message returns after visibility timeout):
aws sqs get-queue-attributes --queue-url "$QURL" --attribute-names ApproximateNumberOfMessages
aws sqs receive-message --queue-url "$QURL" --max-number-of-messages 10 \
  --query 'Messages[].{id:MessageId,body:Body}' > /tmp/dlq.json && jq . /tmp/dlq.json

# 2) Redrive: the body IS the original EventBridge event — re-invoke the target
#    Lambda with it (source "aws.autoscaling" events → openclaw-api; schedule
#    ticks → the scheduled Lambda, or just wait for the next tick):
jq -r '.[0].body' /tmp/dlq.json > /tmp/event.json
aws lambda invoke --function-name openclaw-api \
  --cli-binary-format raw-in-base64-out --payload file:///tmp/event.json /tmp/out.json && cat /tmp/out.json

# 3) Only after a successful re-invoke, delete the message:
aws sqs delete-message --queue-url "$QURL" --receipt-handle "<ReceiptHandle from receive-message>"
```

Schedule-tick events (health/scaler/backup) are safe to just delete — the next tick repeats the work. Lifecycle events must be redriven (or their effects applied manually, see §5d).

### Logs & audit trail

```bash
aws logs tail /aws/lambda/openclaw-api --since 30m --follow
aws logs tail /aws/lambda/openclaw-health-check --since 1h | grep -i "stale\|failover\|migration"
curl -s "${API_URL}audit-log?limit=100" -H "x-api-key: ${API_KEY}" | jq '.[] | {ts, event, object, actor}'
```

## 5. Common failure modes & fixes

### (a) Tenant stuck in `migrating`

**Detect** — migrations should terminate within ~15 min (watchdog):

```bash
curl -s "${API_URL}tenants" -H "x-api-key: ${API_KEY}" | jq \
  '[.[] | select(.status=="migrating")] | map({id, migration_phase, migration_started_at, migration_source, migration_target})'
```

**Fix** — the health-check sweep advances one phase per 5-min tick and its watchdog force-rolls-back anything stuck > 15 min, so first check `openclaw-health-check` is running (Errors alarm, `aws logs tail`). If the sweep itself is broken or you need it back *now*:

```bash
curl -s -X POST "${API_URL}tenants/{id}/cancel-migration" -H "x-api-key: ${API_KEY}" | jq .
```

Then confirm `status=running` and (for cold-mode) that the dashboard answers; `restart` the tenant if the source VM was left stopped. Root-cause via the SSM command IDs in the log (`migration_snap_cmd` / `migration_restore_cmd`):

```bash
aws ssm get-command-invocation --command-id <cmd-id> --instance-id <host-id> \
  --query '{status:Status,err:StandardErrorContent}'
```

### (b) Wedged / unhealthy AZ

**Detect** — host-agent heartbeats `last_seen` + `last_health_check` into `openclaw-hosts` every 15 s; the AZ is considered down when **every** host in it is ≥ 10 min stale:

```bash
aws dynamodb scan --table-name openclaw-hosts \
  --projection-expression "instance_id, az, #s, last_seen, last_health_check, vm_count" \
  --expression-attribute-names '{"#s":"status"}' --output json \
  | jq -r '.Items[] | [.instance_id.S, .az.S // "-", .status.S // "-", .last_seen.S // "never"] | @tsv'
```

Compare `last_seen` to now: < 1 min = healthy; > 10 min = counts toward AZ-failover.

**Fix** — auto-failover fires on the next health-check tick after the 10-min threshold (30-min per-AZ cooldown between rounds; cooldown state lives on the `__az_failover_state__` row in `openclaw-hosts`). To act sooner, `POST /failover/{az}` — **with the §3.3 T3-2 caveat: verify it acted**. Afterward:

- tenants `failover_blocked` (no backup) need a decision: accept data loss and recreate, or wait for the AZ to return. This is the deliberate never-lose-data path.
- tenants `failover_failed_partial`: VM is up on the new host but ALB routing wasn't repointed — check the listener rule for `/vm/<tenant-id>*` points at target group `oc-<last-8-of-target-instance-id>`, fix with `aws elbv2 modify-rule`, then flip the tenant `status` back to `running` (or `restart` it).

### (c) Capacity exhaustion (`create_tenant` returns `pending`, or 4xx)

`POST /tenants` with no host that fits returns `201` with `status=pending` and auto-bumps ASG desired capacity by 1 (capped at `asg.max_capacity`). It returns `400` only for quota violations (`QUOTAS_MAX_*`). Pending tenants are auto-assigned when the new host reaches InService (`HostReadyRule` → `process_pending`).

**Detect headroom** — allocatable = `total_vcpu × cpu_overcommit_ratio` (memory analogous):

```bash
curl -s "${API_URL}hosts" -H "x-api-key: ${API_KEY}" \
  | jq 'map({instance_id, az, status, vm_count, total_vcpu, used_vcpu, total_mem_mb, used_mem_mb})'
aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names openclaw-hosts-asg \
  --query 'AutoScalingGroups[0].{min:MinSize,desired:DesiredCapacity,max:MaxSize}'
```

**Fix**:

```bash
# Immediate capacity (within max):
aws autoscaling set-desired-capacity --auto-scaling-group-name openclaw-hosts-asg --desired-capacity <n>
# Structural: raise asg.max_capacity (and/or overcommit ratios ≤ 4.0) in config.yml, then:
./setup.sh <region> [profile]
```

Tenants stuck `pending` after a host is InService → the launch event may be in the DLQ (§4); redrive it, or trigger assignment manually by invoking `openclaw-api` with a synthetic `{"source": "aws.autoscaling", "detail-type": "EC2 Instance Launch Successful"}` payload.

### (d) Zombie / `deleted` host rows piling up

Since the T2 audit, `cleanup_terminated_host` **hard-deletes** the host row on the ASG terminate lifecycle event — rows should no longer accumulate. If you still see rows for instances that no longer exist, the terminate event was lost (check the DLQ, §4).

**Detect**:

```bash
# Rows in DDB whose instance is gone or terminated:
aws dynamodb scan --table-name openclaw-hosts --projection-expression "instance_id, #s, last_seen" \
  --expression-attribute-names '{"#s":"status"}' --output json | jq -r '.Items[].instance_id.S' \
  | while read -r i; do [ "$i" = "__az_failover_state__" ] && continue; \
      st=$(aws ec2 describe-instances --instance-ids "$i" \
        --query 'Reservations[0].Instances[0].State.Name' --output text 2>/dev/null || echo "gone"); \
      echo "$i $st"; done | grep -v running
```

**Fix** — redrive the DLQ'd terminate event (preferred — it also reaps the row's tenants and completes the lifecycle hook), or clean up manually: first mark/delete its orphaned tenants (`DELETE /tenants/{id}`), then delete the row:

```bash
aws dynamodb delete-item --table-name openclaw-hosts --key '{"instance_id":{"S":"i-XXXX"}}'
```

Never delete `__az_failover_state__` — it holds AZ-failover cooldown bookkeeping.

### (e) Host-agent not heartbeating (stale tenants)

**Symptom** — tenants on one host show `vm_health=stale` / `app_health=unknown` (set by health_check when `last_health_check` in `openclaw-tenants` is > `STALE_SECONDS` = 120 s old; the agent writes at least every `OC_AGENT_DDB_REFRESH` = 60 s, clamped ≤ 110 s).

**Auto-recovery** — when **all** tenants on a host are stale, the next health-check tick runs `systemctl restart host-agent` via SSM (rate-limited to once per 10 min, `agent_restart_at` on the host row). If only *some* tenants are stale it's a per-VM problem, not the agent.

**Manual**:

```bash
# Is the agent alive?
aws ssm send-command --instance-ids i-XXXX --document-name AWS-RunShellScript \
  --parameters 'commands=["systemctl status host-agent --no-pager | head -20","journalctl -u host-agent -n 50 --no-pager"]' \
  --query 'Command.CommandId' --output text
aws ssm get-command-invocation --command-id <id> --instance-id i-XXXX --query StandardOutputContent --output text

# Restart it yourself:
aws ssm send-command --instance-ids i-XXXX --document-name AWS-RunShellScript \
  --parameters 'commands=["systemctl restart host-agent"]'
```

If the *instance* itself is unhealthy (SSM unreachable, ASG marks it), drain is impossible — this becomes case (b): its tenants recover via AZ failover from backups. If SSM works but VMs are broken, `POST /hosts/{id}/drain` first.

### (f) A Lambda erroring / throttling (alarm fired)

```bash
# 1) Which alarm / which function:
aws cloudwatch describe-alarms --state-value ALARM --alarm-name-prefix openclaw \
  --query 'MetricAlarms[].{name:AlarmName,reason:StateReason}'

# 2) Read the stack trace (handlers print full tracebacks):
aws logs tail /aws/lambda/openclaw-<api|health-check|scaler|backup> --since 1h | grep -B2 -A15 -i "error\|traceback"
```

Notes per function:

- **`openclaw-health-check` throttles are semi-expected**: `reserved_concurrent_executions=1` is deliberate (serializes failover/migration sweeps). A throttle means a tick fired while the previous one was still running — sustained throttling means sweeps are chronically slow (many stale hosts / SSM waits); investigate rather than raise concurrency.
- **`openclaw-api` errors**: unhandled exceptions return 500 to the caller; check whether one route is failing (bad DDB row, IAM change) and whether audit rows stopped (`GET /audit-log`).
- **`openclaw-backup` errors**: a failed tenant backup can leave the VM paused only if `backup-data.sh`'s trap failed too — confirm affected tenants are not stuck `paused`, `POST /tenants/{id}/resume` if so.
- A missed schedule tick lands in the DLQ (§4); schedule ticks self-heal on the next interval, so after fixing the code (`./setup.sh` to redeploy), just purge those messages.

## 6. Escalation & data safety

### Production-safety rules (mandatory)

- **Never disable deletion protection or PITR** on `openclaw-tenants` / `openclaw-hosts` / `openclaw-groups` without explicit, recorded justification — they are the authoritative tenant→host→port→ALB mapping.
- **Never `DELETE /hosts/{id}` a host with running tenants** (it hard-deletes them via the lifecycle hook) — drain first (§3.2).
- Prefer read/list/describe over mutate; assume every resource named `openclaw-*` is production when uncertain; get explicit confirmation before any destructive action (`destroy.sh --purge` prompts, don't script around it).
- Never bake `API_KEY` into files served publicly (`console/config.js` deliberately ships it empty).

### DynamoDB point-in-time restore

All control tables have 35-day PITR. A bad bulk edit / accidental wipe is recoverable to any second:

```bash
aws dynamodb restore-table-to-point-in-time \
  --source-table-name openclaw-tenants \
  --target-table-name openclaw-tenants-restore-$(date +%Y%m%d) \
  --restore-date-time "2026-07-24T02:00:00Z"
# Then diff/copy rows back into the live table — PITR restores to a NEW table,
# it never overwrites the live one. VMs keep running throughout (data plane is
# independent of DDB); fix the control plane before mutating tenants again.
```

### Tenant data backup / restore

```bash
# Manual backup (async 202; pause → pigz → S3 → resume):
curl -s -X POST "${API_URL}tenants/{id}/backup" -H "x-api-key: ${API_KEY}" | jq .

# List (orphan backups — source tenant deleted — remain restorable):
curl -s "${API_URL}backups" -H "x-api-key: ${API_KEY}" | jq .

# Restore into a fresh tenant (latest, or pin "timestamp"):
curl -s -X POST "${API_URL}tenants" -H "x-api-key: ${API_KEY}" \
  -d '{"name":"restored-agent","restore_from":{"tenant_id":"<old-id>"}}' | jq .
```

Backups live at `s3://${ASSETS_BUCKET}/backups/<tenant-id>/<timestamp>.gz` with a `backup_retention_days` (default 7) lifecycle — **AZ failover depends on these existing** (no backup = `failover_blocked`), so treat sustained `openclaw-backup-errors` alarms as an availability risk, not just a data-hygiene one.

### Escalation checklist

1. Alarm → §4 to identify function + error; §5(f) for triage.
2. Tenant-impacting? Check `GET /tenants` statuses + Console Logs tab / `GET /audit-log` for what the system last did.
3. Data at risk? Stop mutating, snapshot state (`aws dynamodb scan` the affected table to a file), then act.
4. File issues at the repo (see CONTRIBUTING.md; security issues via its security-notification process — never in public issues).
