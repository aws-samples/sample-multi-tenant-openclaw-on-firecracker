# 解决方案概述

OpenClaw on Firecracker 多租户 AI Agent 平台在 AWS 上为成千上万的租户各自交付一台独立内核的轻量虚拟机，在其中运行带身份、技能与安全护栏的 OpenClaw AI agent。它用 Firecracker microVM 把"越权止于单租户"从容器级别提升到虚拟机级别，并叠加从内容层到凭据层的五层纵深防护，面向需要承载大规模 AI agent、且对租户隔离与性能都有强要求的场景。

## 结论先行：这套方案解决什么、代价是什么

**它解决的核心问题**：多租户共享内核的容器隔离一旦被逃逸，攻击面是整个宿主上的所有租户；本方案给每个租户一台独立 Linux 内核的 Firecracker microVM（与 AWS Lambda、Fargate 同一种轻量虚拟化技术），把单租户的越权或逃逸物理封在它自己的虚拟机里。隔离不靠模型自律，而是落到部署代码与设备：跨租户东西向流量在宿主 iptables 上被丢弃（加固后目标态 100% 丢包），身份走 OpenClaw 原生 Ed25519 非对称认证，凭据用 KMS 信封加密、guest 内零长期 AWS 凭据。

**它的关键取舍**：安全边界下沉到 VM 级换来的是每租户约 2 GB 内存的固定开销（`r8g.metal-24xl` 单台稳态承载约 380 租户，容量推算），以及"改配置必须重建镜像、不热改运行中 VM"的运维纪律。

追求最高密度、能接受共享内核风险的场景，本方案不是最省成本的选择；对隔离强度有合规要求的多租户 AI agent 托管，它把风险面收敛到了单租户。

**它现在的成熟度**：控制面（注册、生命周期、备份、健康检查、AZ failover）与镜像冷注入链路已实测跑通；数据面已从早期的 hub-WS 中枢模型转型为"两级路由直连 microVM gateway"，该链路已在演示环境真机验证但作为 opt-in 能力（`redis.enabled` / `edge.enabled` 默认关闭）。对外性能与容量数字均有一手实测来源，未实测项在对应章节标注为"待核"。

> ⚠️ **注意（部署前必读的三条硬前提）**
>
> - **宿主机型必须带 KVM**：生产基线是 AWS Graviton 裸金属实例 `r8g.metal-24xl`（arm64），用宿主原生 KVM 拉起 Firecracker，**不走嵌套虚拟化**。非裸金属的 Graviton 机型没有 `/dev/kvm`，host 自举会直接失败并被 Auto Scaling 反复替换。详见"部署解决方案 — 问题排查"。
> - **部署机需要 Docker**：AWS CDK 用容器给 AWS Lambda 打包 arm64 原生扩展，部署机（macOS / Windows / Linux 均可）必须有可用的 Docker daemon，否则 `cdk deploy` 会卡在 asset bundling。
> - **`config.yml` 不入库**：仓库只提供 `config.yml.example`，全新克隆后必须先 `cp config.yml.example config.yml`，否则 `setup.sh` 直接报错。

## 核心摘要（两个受众版本）

### 【CTO / 业务视角版】

本方案让你在 AWS 上以 SaaS 形态托管成千上万个互相隔离的 AI agent，每租户一台独立内核虚拟机，把数据泄露与横向渗透的风险面从"整个宿主"收敛到"单个租户"，满足金融等行业对租户隔离与数据残留的合规预期。

控制面全部无服务器（Lambda + DynamoDB + API Gateway），按用量付费、无专用运维服务器；宿主用 Auto Scaling 弹性伸缩，配合内存超卖与 Spot，单台裸金属稳态承载约 380 租户、成本约每租户每月 8.36 美元（推算）。

平台核心与业务解耦，换业务场景只需替换一个"样本"目录，隔离与安全层不变，可快速为不同客户交付自有品牌的 agent 池。

### 【基础架构工程师版】

- **隔离底座**：Firecracker microVM on 宿主原生 KVM（`r8g.metal-24xl`，Graviton4，非嵌套虚拟化）。每租户独立 Linux 内核 + OverlayFS rootfs（只读 base + per-VM 稀疏可写层）+ KMS 加密 EBS。
- **网络隔离**：每 VM 独占一条 `/30` 点对点 TAP 链路，全部落在 `SUBNET_PREFIX/16` 超网内；宿主 iptables 对整个 `/16` 做东西向 `FORWARD DROP`（跨租户 100% 丢包，实测）；每 VM 另插三条规则 DROP 到 IMDS、到租户超网、到宿主管理端口。
- **安全边界（L1–L5）**：L1 内容层 Bedrock Guardrails 输入输出双向；L2 工具层 `before_tool_call` ACL default-deny；L3 身份层 OpenClaw 原生 Ed25519 device 非对称认证 + 控制面 RBAC + `owner_id` 门控；L4 网络层 IMDS 封锁 + DNS Firewall + NAT 出网白名单；L5 凭据层 guest 零长期凭据 + 只读黄金镜像盘 + in-guest auditd/Wazuh 运行时监控。
- **数据面**：浏览器 ─wss `/gw/ws`─▶ 平台后端（验平台 JWT）─ws─▶ ALB ─▶ OpenResty edge ASG（查 ElastiCache Redis 路由表 + strip `/ws/{tid}` 前缀）─▶ microVM gateway:18789（Ed25519 device 握手）。opt-in（`edge`/`redis` gate）。
- **扩展性指标**：microVM 纯启动 1.74s（p50，实测）；单台全健康承载 187 节点（磁盘瓶颈，实测）/ 稳态 380 租户（推算）；per-VM RSS ~609 MB（实测）；大规模建租户经 SQS 削峰绕过 SSM 单实例并发墙。

---

该解决方案利用 Amazon EC2 裸金属实例上的原生 KVM 运行 Firecracker microVM，并由无服务器控制面（AWS Lambda、Amazon DynamoDB、Amazon API Gateway）管理租户的注册、生命周期、备份与注销，提供以下能力：

- 为每个租户预配一台独立内核的 Firecracker microVM，在虚拟机级别隔离租户之间的内存、CPU 与内核。
- 将身份、技能、配置在虚拟机启动前冷注入到只读黄金镜像，虚拟机启动即为成品，运行后控制面不向其注入任何业务数据。
- 通过两级路由（平台后端 → OpenResty 边缘 → microVM gateway）把浏览器的实时聊天请求按租户直连到对应虚拟机内的 OpenClaw agent，microVM 只对宿主内部暴露端口，不开放公网入站。
- 以 OpenClaw 原生 device 非对称认证（Ed25519）为数据面身份根，控制面以 `x-api-key` + 可选 Cognito RBAC 守门；验签失败一律降级到最小权限。
- 叠加五层纵深防护：内容层、工具执行层、身份层、网络层、凭据与只读监控层，每一层都落实到部署代码或设备，不依赖模型自律。

本实施指南概述参考架构与组件、部署规划注意事项，以及将其部署到 Amazon Web Services (AWS) 云的配置步骤。它面向在 AWS 云中具有架构实践经验的平台工程师、安全评审人员、运维工程师与应用开发人员。

> **Note**
>
> 平台核心与具体业务解耦。控制面、数据面与宿主生命周期脚本不包含任何业务内容，只负责"预配并管理大规模隔离的 AI agent microVM"。每台虚拟机运行什么 agent，由一个可替换的"样本"决定：构建脚本通过 `SAMPLE` 环境变量选择样本，默认 `finance-agent`。随仓库发布的 `finance-agent` 是一个最小骨架样本（身份人设 + 标配安全护栏 + `weather` 与 `skill-vetter` 两个演示技能），具体业务能力由部署方按自身场景在样本目录内填充，平台核心与安全层不随之改变。

## 功能

**虚拟机级租户隔离**

为每个租户预配一台独立内核的 Firecracker microVM，在硬件辅助虚拟化层面隔离租户的内存与 CPU，使单个租户内的越权或逃逸止步于该租户自己的虚拟机，不波及其他租户或宿主。

**启动即成品的冷注入交付**

将身份、技能、护栏与配置在虚拟机启动前冷注入到只读黄金镜像盘，虚拟机启动即带完整身份与护栏。运行后控制面不向虚拟机注入任何业务数据，修改身份或技能需重新构建镜像，而非热改运行中的虚拟机。

**五层纵深安全防护**

叠加内容层（Amazon Bedrock Guardrails）、工具执行层（agent 进程内 ACL 护栏）、身份层（OpenClaw 原生 Ed25519 device 认证与控制面基于角色的访问控制）、网络层（宿主 iptables 与 DNS 防火墙）、凭据与只读监控层五层防护，每一层都落实到部署代码或设备。

**两级路由数据面**

平台后端 WebSocket 网关 + OpenResty 边缘 + 宿主 DNAT 两级路由，把浏览器的实时聊天按租户直连到虚拟机内的 OpenClaw gateway。虚拟机只对宿主内部 TAP 网卡暴露 gateway 端口，不在公网开放任何入站端口。

**无服务器控制面**

注册、生命周期、健康检查、备份、扩缩容逻辑由 AWS Lambda、Amazon DynamoDB 与 Amazon API Gateway 承载，按用量付费，无需运维专用服务器。

**默认高可用**

默认以 2 台宿主跨多个可用区（Availability Zone）部署（`multi_az.enabled` 与 `az_failover.enabled` 默认均为 `true`），当某个可用区内所有宿主持续不健康时，自动把受影响租户从最近备份恢复到健康可用区，恢复前强制校验备份存在（无备份则拒绝迁移，数据安全优先于可用性）。

**可替换的业务样本**

平台核心与业务样本分层。更换业务场景只需替换样本目录，控制面、隔离机制、安全层与运维工具均不变。

## 优势

**更强的租户隔离边界**

与共享内核的容器多租户相比，独立内核的 microVM 把隔离边界下沉到虚拟机级别，缩小了横向移动与逃逸的攻击面。

**防御不依赖模型自律**

每一层防护都落实到部署代码或设备：工具执行层在工具真正执行前否决危险动作，网络层在宿主 iptables 上丢弃跨租户流量，即便提示词注入绕过模型，敏感操作仍被拦截。

**配置变更可审计、可回滚**

遵循"改部署代码再重建"的纪律，身份、技能、配置的变更随镜像重建继承，可灰度、可回滚，运行后不开放宿主到虚拟机的热注入通道。

**按用量付费的弹性容量**

宿主由 Amazon EC2 Auto Scaling 管理弹性伸缩，控制面采用无服务器服务，容量随负载扩缩。

**实测验证的性能与安全结论**

关键性能、容量与安全结论均有一手实测来源（参见架构详情与规划部署），未实测确认的项在对应章节如实标注为"待核"。

## 使用案例

**大规模 AI agent 托管**

为成千上万的终端用户或租户各自托管一个隔离的 AI agent 实例，并对它们做统一的生命周期与资源管理。

**对隔离强度有合规要求的多租户场景**

在金融等对租户隔离与数据残留有强要求的行业，用虚拟机级隔离满足"单租户越权不外溢"的合规预期。

**面向终端用户的 AI 助手自助开通**

允许已登录的终端用户为自己开通 AI agent 节点，由平台按每用户配额与授权策略门控。

**带安全护栏的 agent 平台交付**

向需要内置越狱拦截、恶意技能拦截、凭据外泄拦截的客户交付一套开箱即带护栏的 agent 平台，并以可替换样本承载具体业务能力。

## 概念和定义

以下是平台特有的重要概念与术语。完整术语见本指南的术语表。

**租户（Tenant）**

隔离与计费的基本单位。每个租户对应一台 Firecracker microVM，由唯一的 `tenant_id`（DynamoDB 主键 `id`）标识。

**microVM**

由 Firecracker 在 KVM 之上启动的轻量虚拟机，具备独立内核、毫秒级启动、强隔离特性。平台为每个租户预配一台 microVM。

**冷注入（Cold injection）**

在虚拟机启动前将身份、技能、凭据、配置写入磁盘的过程，与运行后的"热注入/热改"相对。平台所有身份与配置变更均走冷注入，运行后不热改虚拟机。

**只读黄金镜像（Read-only golden image）**

烤入身份文件与权威技能的只读镜像盘，以 Firecracker 的写屏障（`is_read_only:true`）、guest 内 `mount -o ro`、只读绑定三层叠加保证 agent 在虚拟机内无法篡改身份。

**控制面（Control plane）**

由 AWS Lambda、Amazon DynamoDB、Amazon API Gateway 构成的管理平面，负责租户注册、生命周期、备份、注销，运行后不向虚拟机注入业务数据。

**数据面（Data plane）**

承载实时聊天的两级路由链路：平台后端 WebSocket 网关 → OpenResty 边缘（查 Redis 路由表）→ 宿主 DNAT → 虚拟机内 OpenClaw gateway。

**纵深防护五层（Defense in depth）**

安全模型自外向内为内容层、工具执行层、身份层、网络层、凭据与只读监控层，每层独立生效、互为正交。

**样本（Sample）**

承载具体业务能力的可替换目录。平台核心与样本分层，更换样本即更换整套 agent 能力，控制面不变。
